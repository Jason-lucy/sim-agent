## D-001 · 2026-09-23 · 为什么仿真内核用 SimPy 而不是自研

**背景**：原始设想是「自研一款 AI 原生离散事件仿真软件」。可行性评估（竞析/数析/路径三线调研）结论：内核层是硬壁垒但已有成熟开源解；个人做内核是纯工作量黑洞，且不体现 Agent 工程能力。

**决策**：采用 SimPy（MIT）作为仿真内核，不自研。

**理由**：对 Agent 项目，内核选型的第一标准不是「它好不好用」，而是「**LLM 能不能可靠地为它生成代码**」。SimPy 是纯 Python、学术界事实标准、LLM 训练语料最充分、生成代码正确率最高。竞品调研显示 AnyLogic 官方演示的 LLM 建模也是走 Python API 路线。

**放弃的方案**：Salabim（生态小、LLM 语料少）、JaamSim（Java 系，跨语言集成成本高）、自研（正确性风险极高，与转行目标错配）。

## D-002 · 2026-09-23 · 为什么用「模板优先 + LLM 兜底」而不是让 LLM 直接生成代码

**背景**：LLM 端到端生成 SimPy 代码「能跑」但不可靠——语法对、语义错（分布写反、资源数错），且失败时无法定位是「理解错」还是「写错」。学术佐证：人大 SimLLM 论文指出「可执行 ≠ 机制正确」。

**决策**：生成层采用「参数化模板优先，LLM 兜底 + 自修复」架构。LLM 的职责收敛为：①选模板 ②填参数（经 JSON Schema 校验）③模板覆盖不到时才生成代码，且必须过冒烟执行 + 报错回灌自修复（≤3 次）。

**理由**：把「看运气」变成「接近确定」。同时这套三道防线本身就是作品集最有说服力的部分——证明作者理解 LLM 的不可靠性并有工程手段兜住。

## D-003 · 2026-09-23 · 为什么 LLM 选 DeepSeek（API 接入）

**背景**：用户约束「有开源的就用开源的」。完全本地方案（Ollama + Qwen2.5-7B）零 API 费但速度慢、结构化输出质量打折。

**决策**：默认 DeepSeek API（开源权重模型的官方服务），通过 openai SDK 的 OpenAI 兼容协议接入。

**理由**：便宜、中文强、结构化输出可靠、模型权重开源；协议兼容保证**随时可换** Qwen / Ollama / 任何兼容服务，不被一家锁死。API Key 只存 `.env`（已 gitignore），不进仓库。

**放弃的方案**：本地 Ollama（留作后期可选路线： demonstrating 本地部署能力时切换）。

## D-004 · 2026-09-23 · 为什么项目定位是「Agent 系统」而不是「仿真软件」

**背景**：可行性评估的核心判断——题材（DES）与转行目标同构（Visual Logic 的事件驱动心智 ≈ Agent 的工具调用链），但「做软件」会把时间吸进内核/GUI 的软件工程黑洞。作品集的说服力来自 Agent 工程能力（可靠性/评估/部署三条面试必答题），不来自「仿真软件」这个壳。

**决策**：项目 = 「自然语言 → 可运行可验证仿真模型的 Agent 系统」，DES 是第一个垂直场景。核心资产是评测集（30 条场景）与可靠性工程。

**放弃的方案**：通用「AI 原生仿真软件」（市场窗口以季度计收窄，且个人无法在功能上追赶头部厂商）。

## D-005 · 2026-09-23 · 环境决策：Git 使用 WorkBuddy 内置 PortableGit，Python 使用托管版 3.13

**背景**：本机（工作机）未装 Git；WorkBuddy 自带 PortableGit（`binaries\PortableGit\...\cmd\git.exe`）可直接调用。

**决策**：Git 直接调用内置 PortableGit（免安装、免管理员权限）；Python 使用托管版 3.13.14；虚拟环境建在项目内 `.venv`（隔离，不污染系统）。

**备注**：若后期需要独立 Git（如配 GitHub Desktop / SSH），再安装官方 Git for Windows。

## D-006 · 2026-09-23 · 定位收窄：面向非制造业的商业/服务业场景

**背景**：用户提出——中国商用 DES 很少（调研已证实：国产厂商集中在军工，商业流程 DES 近乎空白），且制造业对数据精度要求高（节拍时间、MTBF/MTTR、换型时间），粗数据做不出可信模型。因此将产品定位主要面向**非制造业的商业场景**。

**决策**：目标场景族从「排队/生产」收窄为「**排队/服务流程**」：客服中心、银行网点、医院门诊/急诊、餐饮翻台、门店收银、政务大厅等。

**理由（支持面）**：
1. 与调研数据同向：国产商业流程 DES 空白 = 真实市场缝隙；Simul8 等厂商在中国服务业渗透也低
2. 服务业容量决策（加几个坐席/收银台）对数据精度容忍度高——粗参数也能出方向性结论，放大「AI 把模糊描述变可跑模型」的价值；制造业恰恰相反，精度门槛会把个人产品的可信度打死
3. 与学术工作（Leuphana/SimLLM 都做制造/物流）错位，差异化更清晰
4. M/M/c 数学内核不变，改的只是模板皮肤与评测集措辞——**当前改造成本近乎零，P2 后再改就要返工**

**诚实记录的 tradeoff**：
1. 服务业付费能力中低（调研：部门预算、短决策链）→ 商业化阶段的变现难度高于制造业；作品集阶段无影响
2. 服务业流程数据普遍更缺 → MVP 靠用户口述参数兜底，中期可加「波峰时段」等结构化提问引导补参

**落地变更**：P2 模板库「串行多工站产线」→ 替换为「多阶段服务流程（前台→服务→收银）」；30 条评测集全部改写为服务业场景；non-goals 增补制造业场景为当前版本非目标。

## D-007 · 2026-09-23 · P2 可靠性工程的三个设计决策

**背景**：P2 是全项目最有价值的资产（评测集 + 可靠性工程），目标：30 条评测一次通过率 ≥70%、自修复后 ≥90%。

**决策 1｜模板覆盖 5 种模型类型，但全部保持「静态模板 + 数据内嵌」**：
M/M/c（P1 已有）、finite_queue（等位区上限+流失）、multi_stage_line（多阶段服务链）、peak_arrival（高峰/平峰分时段到达，薄化法实现非齐次泊松）、priority_queue（VIP 优先，simpy.PriorityResource 非抢占）。
结构化数据（阶段表/时段表）用 Python repr 内嵌为字面量，模板运行时读取——**模板本体始终静态，LLM 永远不写自由代码**，只决定「选哪个模板 + 填什么参数」。这是防线②的彻底形态。
放弃的方案：Jinja2（M1 起零依赖原则仍然成立，模板规模未到需要它的程度；记入待议）。

**决策 2｜自修复（防线③）修的是 spec，不是代码**：
运行/渲染失败时，把「当前 spec + 报错」回灌 LLM 修正 spec 后重新走「渲染→运行」，而不是让 LLM 改生成的代码。理由：代码由模板生成、天然正确；出错根源几乎总在 spec 参数与 schema/时长约束的矛盾。修 spec 同时保证修复后的代码仍走模板路径，正确率不会被「修复补丁」污染。

**决策 3｜评测断言分五层，利用率对照理论 ρ（±0.10）是最有分量的断言**：
A1 管线跑通 / A2 model_type 正确 / A3 参数解析正确（数值 rel≤5%，整数精确）/ A4 结果合理（利用率≤100%、等待≥0、有完成量）/ A5 **sim_util 与理论 ρ 偏差≤10pp（仅当 ρ<0.9）**。
A5 直击 SimLLM 论文指出的「可执行 ≠ 机制正确」：生成的模型不仅要能跑，还要跟排队论真值对得上。评测集里所有场景都预先核算过理论 ρ<0.9（保证断言适用），且措辞刻意多样化（秒/小时换算、百分比 VIP、「前两个半小时」等），防止单一措辞过拟合。

**修订（同日实测后）｜A5 容差改为自适应：max(10pp, 2.5σ_noise)**：
首轮回归 30 条只过 63.3%，排查发现两类问题，都不是引擎 bug：
1. multi_stage 模板警告条件里引用了不存在的键（`mean_service_min` 应为 `mean_service`）——**模板 bug 是 spec 自修复救不了的**（自修复改 spec，改不到模板），防线职责边界由此验证：防线③只能兜「参数错」，兜不了「模板错」，模板正确性只能靠模板自身的测试保障。
2. 6 个场景 A5 误报：短时长场景期望到达数仅 40~60，利用率抽样噪声（±10~15pp）与固定容差同量级。**断言在统计上不成立，错的是断言不是数据**。
修正：①拉长小样本场景时长（期望到达 ≥60）②A5 容差 = max(10pp, 2.5σ)，σ=E[S]·√(2n)/(c·T) 解析算出；大样本仍严格 10pp。方法论价值：评测断言本身也要过统计审查——这是「用 eval 驱动开发」的真实一课，进作品集叙事。

## D-008 · 2026-09-23 · 经验引擎（P2.5）：不微调模型，「越跑越好」来自检索增强与上下文工程

**背景**：用户需求——系统应具备不断优化迭代的能力：一次比一次准确，每跑一次吸收一次经验，运行速度越来越快、越来越流畅、准确率越来越高。

**决策 1｜改进来源 = 三层记忆，不是模型训练**：
个人项目无算力无数据，且 API 模型不可训练。三个愿望分别落到三个机制：速度 → **缓存层**（场景指纹命中 → 0 次 LLM 调用秒回）；准确 → **示例层**（同类型成功 spec 作 few-shot 注入抽取 prompt——LLM 没变聪明，是上下文变好了）；流畅 → **规则层**（失败轨迹提炼避坑提示，人工确认后注入）。

**决策 2｜相似度用中文字符 bigram Jaccard，不上 embedding**：
场景族锁死排队/服务类（D-005/D-006），关键词重叠足以支撑「找同类场景」；零新依赖、完全可解释。场景族扩宽后再议向量检索。检索排除与查询完全同文本的案例——示例注入验证的是**经验迁移**，不是把答案抄回去（对照评测的公平性依赖这条）。

**决策 3｜防污染闸门是经验系统的生命线**：
经验系统经典死法：一次错误运行被存为「经验」，此后每次被当示范，系统性带偏所有后续运行。闸门设计：①只有「跑通且合理性验证无违规」的运行才能进缓存/示例层（store.add_exemplar 强制 validated=True，未验证写入直接抛异常）②失败案例只进规则层且需人工确认才注入 ③缓存代际号 = f(模板内容, schema 内容, 引擎版本)——任何模板修改 → 代际变化 → 全量缓存失效，绝不命中旧代码的结果 ④JSONL 明文进 Git，每条经验可追溯可人工剔除。

**决策 4｜冷启动诚实声明**：前 20~30 次运行经验库太薄，提升不可见——这是数学事实。验收门 B 的对照设计（B 组 8 条易错场景：满库 vs 空库）就是要求数据说话，小样本不显著则如实记录。

**落地变更**：`src/memory/`（store.py / retrieve.py）、pipeline 四步接入（缓存短路 → 经验检索注入 → 验证后写回）、extractor 支持 exemplars/rules 注入、run_evals 双模式（满库主跑 / --replay-empty 空库对照）、history.jsonl 演进记录、trend.py 趋势图、12 项单元测试（闸门/代际失效/相似度/坏行容错）。
